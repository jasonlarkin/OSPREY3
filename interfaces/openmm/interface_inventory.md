# OpenMM: interface inventory

OpenMM decomposition:

## Object graph (core)

- **`System`**
  - owns particles, constraints, and a list of `Force` objects.
- **`Force` (front-end term)**
  - user-facing configuration of a term.
  - produces a backend object via `createImpl()`.
  - has **force-group** support (grouping subsets of terms for evaluation scheduling).
- **`ForceImpl` (back-end term)**
  - actual evaluation hook used by the engine.
  - created per `Context` (enables per-context caching/resources).
- **`Context` / `ContextImpl`**
  - binds together: `System` + `Integrator` + `Platform` + runtime state (positions, velocities, parameters).
- **`Platform`**
  - selects an implementation backend (CPU/OpenCL/CUDA/other) by providing required kernels.
  - acts as a registry of `KernelFactory` objects.
- **`Kernel`**
  - the backend unit that actually executes computation (often mapped to device kernels).

## Structural pattern (high value)

- **Front-end/back-end split**: `Force` is configuration; `ForceImpl` is per-context evaluation.
- **Backend registry**: `Platform` provides the “how it runs” separation from “what it computes”.
- **Term composability**: energy is a sum of independent `Force` objects attached to a `System`.

## Extensibility seams to map explicitly

- adding a new **term**
- adding a new **platform**
- adding a new **custom term** mechanism (already exists via `Custom*Force`)
